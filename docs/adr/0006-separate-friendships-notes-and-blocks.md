# ADR 0006: 友達関係・個別メモ・ブロックを分離する

## Status

Accepted

## 背景

友達は公開`users.user_id`を使って承認なしで追加し、追加後は双方の友達一覧へ表示する。詳細画面では追加者と追加日時を表示し、各ユーザーが相手に対して自分だけのメモを編集できる必要がある。

ブロックは操作したユーザーのブロックリストにだけ表示する一方、通常の友達一覧・送金候補・請求候補からは双方を非表示にする。

## 課題

- 相互の友達関係を重複なく保存する
- 追加者と追加日時を保持する
- 同じ友達関係に対してユーザーごとに異なるメモを保持する
- ブロックの方向と、双方を遮断する表示ルールを両立する
- 公開`user_id`が将来変更されても関係を壊さない

## 選択肢

1. `friendships`の1行へstatusと双方のmessageをすべて持たせる
2. 友達関係、個別メモ、ブロックを別テーブルへ分離する
3. ユーザーごとの片方向contactsとして保存する

## 採用した案

選択肢2を採用する。

- `friendships`: 正規化した2ユーザーの組、追加者、追加日時
- `friendship_notes`: 友達関係と所有ユーザーごとの非公開メモ
- `user_blocks`: blockerからblocked userへの方向付きブロック

`friendships.user1_id < friendships.user2_id`を保証し、同じ組み合わせを一意にする。友達追加APIでは公開`user_id`から対象を検索するが、保存する外部キーには内部`users.id`を使う。

追加者のメモだけ友達追加時に作成する。追加された側はnoteレコードなしを`null`として扱い、初回編集時に作成する。

どちらか一方の`user_blocks`が存在する場合、通常の友達一覧・送金候補・請求候補では双方を除外する。ブロックリストには`blocker_id`がcurrent userのレコードだけを表示する。

## 採用理由

- 相互関係を1行にでき、重複をDB制約で防げる
- 個別メモの更新が相手のメモへ影響しない
- ブロック解除後も友達関係とメモを保持できる
- ブロック方向を失わず、双方遮断の検索条件にも利用できる

## メリット

- 責務とアクセス制御の境界が明確
- 将来のメモ編集・ブロック解除へ対応しやすい
- 公開ID変更の影響を受けない

## デメリット

- 友達一覧取得時に複数テーブルのJOINが必要
- noteのuserが友達関係の参加者かどうかはapplication層でも検証する必要がある
- 送金・請求候補取得にもブロック除外条件を追加する必要がある

## 将来的な見直し条件

- 友達申請と承認フローを導入する場合
- 友達削除や再追加時の履歴を保存する場合
- ブロック以外にミュートや表示制限を追加する場合
