# ADR 0005: 請求ワークフローを送金履歴から分離する

## ステータス

採用

## 背景

送金は実行時点で金額移動が完了する一方、請求は被請求者の承認または拒否を待つ。複数人への請求では、各被請求者が独立して応答し、金額も個別に設定される。

## 課題

- `pending`の請求を完了済みの送金履歴と混同しない
- 複数の被請求者が個別に承認・拒否できる
- 拒否された請求を削除せず追跡できる
- 承認時に残高更新と送金履歴作成を同一DB transactionへまとめられる

## 選択肢

1. `transfers`へ`pending / accepted / rejected`を追加する
2. `pending`だけを一時テーブルへ保存し、応答後に削除する
3. `payment_requests`で請求状態を管理し、承認時だけ`transfers`へ完了履歴を作る

## 採用した案

選択肢3を採用する。`payment_requests`は1被請求者につき1行とし、`requester_id`、`recipient_id`、個別の`amount`、`status`、応答日時を保持する。

## 採用理由

- `transfers`を実際に完了した金額移動だけの履歴として保てる
- 請求の承認・拒否という状態遷移を独立して表現できる
- 複数人請求でも各行を個別に更新でき、不要な親バッチを増やさない
- 承認処理で残高更新、`transfers`作成、請求状態更新を一つのDB transactionにできる

## メリット

- 未承認の請求を送金完了として表示する事故を防げる
- 拒否履歴を残せる
- 一覧取得用indexを請求側の要件に合わせられる
- 将来の認証方式に関係なく、内部UUIDで当事者を参照できる

## デメリット

- 承認済み請求と`transfers`の関連を必要とする場合、関連カラムの追加が必要になる
- 請求と送金の二つのテーブルを整合させるtransaction実装が必要になる
- 複数人への一括操作そのものを追跡するbatch IDは現時点では持たない

## 将来的な見直し条件

- 一括請求単位の取消・タイトル・メモが必要になった場合
- 承認済み請求から対応する送金履歴へ直接遷移する要件が決まった場合
- 分割承認や一部支払いが必要になった場合
