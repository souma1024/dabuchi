# ADR 0003: 送る相手候補一覧にカーソルページングを採用する

## ステータス

採用

## 背景・課題

ユーザー選択画面では、自分以外のユーザーを20件ずつ無限スクロールで表示する。取得中にユーザーが追加された場合でも、ページ間の重複や取りこぼしを抑える必要がある。

## 選択肢

1. `OFFSET` / `LIMIT`によるページング
2. `created_at`と内部UUIDを使うカーソルページング
3. 全件取得してフロントエンドで分割

## 採用した案

`created_at ASC, id ASC`を安定した並び順とし、最後に返した行の値を不透明なカーソルへ変換する。各取得では表示件数より1件多い21件を問い合わせ、次ページの有無を判定する。

## 採用理由

- 無限スクロールと相性がよい
- 途中でデータが追加されても`OFFSET`方式より重複・取りこぼしが起きにくい
- 同一作成日時でも内部UUIDを第2キーにして順序を一意にできる
- DBから必要な件数だけを取得できる

## メリット

- データ量が増えても大きな`OFFSET`を読み飛ばす必要がない
- API利用側は`nextCursor`をそのまま渡せばよい
- DBの内部並び順をAPI利用側へ露出しない

## デメリット

- 任意ページへの直接移動には向かない
- カーソル形式を変更する場合は後方互換性を考慮する必要がある
- 現在のusers migrationには一覧用複合indexがないため、データ量増加時に追加検討が必要

## 見直し条件

- ページ番号による直接移動が必要になった場合
- users件数の増加により実行計画や応答時間が許容範囲を超えた場合
- 検索や並び替え条件を追加する場合
